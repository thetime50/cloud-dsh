# 0.0.0 切片：多实例基座、沙箱对接、App Agent

本文件是 0.0.0 的一部分，不是整个 0.0.0。

0.0.0 的原则：功能先跑通，不做权限体系，只留兜底。本切片只做三件事：

1. 多实例服务基座（一个容器里多个 DSH 实例）
2. 基础沙箱对接（用户脚本和文件进出沙箱）
3. App Agent 管理，以及两个平台内置应用：base app、空白 rag app

隔离方式按实例：一个用户对应一个（可能n个） `dsh-profile 实例 + 沙箱`。这个对应关系由主站 play-site 保存。本服务只管理实例，不做一用户一容器。

## 2. 假定

本仓库还没有 DSH 源码。下面三条不成立时，只改适配层，不改基座和沙箱契约。

1. DSH 能以独立进程启动，配置落在一个 profile 目录，HTTP 只绑本机端口。不改 DSH 源码。
2. 应用市场的条目能出现在 DSH 新建会话的选项里。用户选中后套上该应用的默认配置。基座不代建会话。
3. Python / Node / Shell / 文件工具能改成调用外部命令 `sandbox-run`。

外围主站 play-site 负责登录、用户身份、用户与实例的绑定、默认 LLM Key。本服务不建用户表，也不保存绑定。

## 3. 运行形态

一个容器，一个入口进程 `cloud-dsh`。它拉起两样东西：

- `gateway`：唯一对外端口。把本次访问的实例 id 和 cookie 交给主站确认；主站认为实例、用户、登录状态满足权限后，再转到该实例的 DSH
- `launcher`：实例的创建、启停、崩溃拉起

每个用户实例是 launcher 拉起的一个 DSH 子进程，不是一个新容器。共享只读层在镜像里：DSH 可执行文件、平台插件、Python/Node 运行时。用户可写数据在 `/storage`。

```
play-site  http://xx.yy.com/
   签发 JWT；cookie Domain=xx.yy.com
   用户到实例的绑定、默认 LLM Key 在主站

浏览器直连 http://dsh.xx.yy.com
   基座在另一台机器时，公网 frps 把该域名转到基座上的 frpc，再进 gateway
   页面不经主站转发
   | 把本次实例 id 和 cookie 交给主站确认权限
   | 通过后只转到本机 127.0.0.1:<该实例端口>
   v
DSH 进程（一用户一个）
   | 脚本与文件
   v
sandbox-run
   工作根：该实例 files/
   不带：/private、其他实例目录、API Key
```

DSH 进程持有 Key。用户脚本只经 `sandbox-run`，一层。不在 DSH 自带沙箱外面再套，也不改成只钉 `sandbox-policy` 的做法。

运行在一个 Linux 容器里。开发机是 Windows 时也进这个容器。沙箱不是一用户一容器。

基座没有公网入站时，用 frp 露出 gateway：frps 在公网入口，frpc 与基座同机。浏览器访问的主机名仍是 `dsh.xx.yy.com`，cookie 照常带上。frp 只打通这条入站，不解析登录，不代替主站确认权限。基座向主站确认时走自己的出站。WebSocket 与页面走同一条隧道。

## 4. 模块

| 模块 | 职责 |
| --- | --- |
| gateway | 本服务的管理页自己处理；打开实例时把实例 id 和 cookie 交给主站确认，通过后转发到该 DSH 页面 |
| frp | 基座无公网入站时，frpc 把 gateway 暴露为 `dsh.xx.yy.com`。不转发业务，不保存绑定 |
| launcher | 实例生命周期；分配端口；写 profile；监督子进程 |
| sandbox-run | 脚本和文件的出口：工作根、越界拒绝、去掉密钥、超时 |
| 应用市场 | 独立模块。条目装进实例，供 DSH 新建会话时选择；应用列表页读这里 |
| 管理页 | 本服务自己的页面。0.0.0 预留，应用列表页占一个入口 |
| dsh 适配 | 启动参数与健康检查。会话和消息留在 DSH 页面 |

状态放一个 sqlite：`/private/infrastructure/control.db`。表里只有实例，没有用户，也没有用户到实例的绑定。

## 5. 目录

```
/opt/dsh/                         只读，镜像内
/opt/runtime/                     只读，python / node
/opt/apps/base/                   DSH 插件，只读
  app.json                        只给列表页
/opt/apps/rag-blank/              继承 base 的插件，只改启动提示语
  app.json

/storage/instances/{instanceId}/
  shared/                         只读共享，本切片可为空目录
  dsh-profile/                    该实例的 DSH 配置与会话数据
  files/                          沙箱里的读写根

/private/
  infrastructure/control.db       实例、密钥引用
  archives/                       本切片不使用，不挂载
```

`dsh-profile` 就是该实例的 `DSH_HOME`，给 DSH 进程用，不交给 `sandbox-run`。会话因此不会被用户脚本读到。`shared` 只读，`files/` 可写；`/private` 不在这次执行的可见范围内。

## 6. 本服务写在本机的内容

主站上的绑定、DSH 里的会话不写进这里。

### 6.1 实例表

存在 `/private/infrastructure/control.db`。一行一个实例。

| 字段 | 说明 |
| --- | --- |
| id | 实例 id |
| status | created / running / stopped / deleted |
| port | 仅 127.0.0.1 |
| pid | 当前子进程 |
| profile_dir / files_dir | 第 5 节里的 `dsh-profile/`、`files/` |

基座不保存会话。会话在该实例的 `dsh-profile` 里，由 DSH 页面自己读写。

### 6.2 应用展示文件

应用本身是 `/opt/apps/<id>/` 里的 DSH 插件。旁边的 `app.json` 只给 `/manage/apps` 读名称和说明，不进数据库，也不参与会话配置：

```json
{ "id": "base", "name": "基础助手", "kind": "base", "description": "通用助手" }
```

```json
{ "id": "rag-blank", "name": "知识库", "kind": "rag", "description": "继承基础助手，知识库尚未接入" }
```

默认配置在插件里。`rag-blank` 继承 `base`，只改会话启动提示语。新建会话时选中的是这个插件。

### 6.3 沙箱日志

不建表。`sandbox-run` 每次执行追加一条日志。`workspaceId` 本切片等于 `instanceId`。`sessionId` 有则记下。

```
userId, workspaceId, sessionId, agentId, taskId, workerId, traceId
```

`workerId` 用实例 id。来源以 launcher 启动该进程时写入的实例身份为准，不采用脚本自报的 id。

## 7. 行为

### 7.1 身份

主站是 `http://xx.yy.com/`。本服务是 `http://dsh.xx.yy.com`，可以落在另一台机器上。浏览器直连这个域名。基座没有公网入站时，由公网 frps 接到基座侧 frpc，再进入 gateway。请求不经主站转发。

主站把 cookie `play_site_token` 的 Domain 设为 `xx.yy.com`（httpOnly、`path=/`、不设 Secure）。`dsh.xx.yy.com` 是它的子域，浏览器访问时会带上这枚 cookie，换一台服务器也一样。页面仍直连本服务。本服务不发登录 cookie，不接受 `X-User-Id`。

打开某个实例时，访问地址里已经有实例 id。gateway 把这个实例 id 和这枚 cookie 交给主站。主站确认：登录有效、该用户仍绑定这个实例、当前权限允许进入。三项都满足才返回通过。基座不自己判断登录和绑定，也不根据用户去查「该进哪个实例」。主站不通过就不转发，也不创建实例。

LLM Key 从 play-site 的用户配置取，写入该 DSH 进程的环境。取不到就用部署时的默认 Key，仍然只进 DSH 进程。

### 7.2 实例

本服务按实例 id 管理进程。主站确认通过后，gateway 对这次访问的实例 id 做 `ensure`：目录没有就创建并启动，停着就启动，已经在跑就直接用。实例记录由主站事先调用创建接口写入。

- 启动：选择 `127.0.0.1` 上的空闲端口，写 profile，拉起 DSH，健康检查通过后标为 running。命令是 `dsh --profile web --port`，`DSH_HOME` 指向该实例的 `dsh-profile`，由 launcher 传入，不写进实例 `.env`。Node ≥ 24.9。就绪看本机 HTTP 是否应答，不靠固定等待。空闲回收不在本切片
- 停止：杀掉该子进程，状态改为 stopped，目录保留
- 删除：先停止，状态改为 deleted，目录保留。本切片不提供抹盘
- 进程异常退出：launcher 最多再拉起 3 次，仍失败则 stopped
- 入口进程重启：扫描表，把 running 但 pid 已不在的实例重新拉起

管理接口只给运维，本切片不做角色系统，用单独的管理令牌：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | `/admin/instances` | 创建并启动，返回实例 id。绑定由主站写入 |
| POST | `/admin/instances/{id}/stop` | 停止 |
| POST | `/admin/instances/{id}/start` | 启动 |
| DELETE | `/admin/instances/{id}` | 标记删除 |
| GET | `/admin/instances` | 列表 |

### 7.3 用户访问

用户打开 `http://dsh.xx.yy.com`，cookie 由浏览器直接带上。

**DSH 页面**  
基座不提供会话和消息接口。用户打开地址里指定的那个实例。主站确认通过后，gateway 对该实例做 `ensure`，把 HTTP 和 WebSocket 转到 `127.0.0.1:<port>`。确认结果以外的地址不能当作上游。

**本服务的管理页（预留）**  
挂在 gateway 上，不进 DSH。路径放在 `/manage` 下，以后增加的管理页都在这里。0.0.0 只预留这个区和其中的应用列表页 `/manage/apps`：列出镜像内的 `base` 与 `rag-blank`（名称、类型、一句说明），只读，不能安装或修改。未登录打不开。这一版不把管理页列入完成标准。

### 7.4 沙箱

对接在 `sandbox-run`。DSH 的 Python / Node / Shell / 文件工具调用它。不用旧稿那种只钉 `sandbox-policy.workspaceRoot`、再靠 DSH 自带 `sandbox-local` 的做法。

```
sandbox-run --instance <id> --timeout 30s -- <py|node|sh> ...
```

实例 id 必须在控制库里，工作根用库里的 `files_dir`，忽略调用方传入的其它路径。0.0.0 只固定这些：

- 写入落在该实例 `files/`；`..` 和 `files/` 以外的路径拒绝
- 不把 `/private`、`dsh-profile`、其他实例目录交给这次执行
- 环境只留 `PATH`、`LANG`、`TMPDIR`、`HOME`，没有 API Key
- 超时 30 秒，stdout/stderr 各截断到 1MB，超时则结束这次执行，DSH 进程还在

只此一层。nsjail 的具体配置不在本切片展开。网络保持直连。

### 7.5 应用市场

市场独立于 launcher。一条应用是一个 DSH 插件。用户在 DSH 页面新建会话时选中它，套上插件里的默认配置。`app.json` 只负责列表上的名称和说明。

进行插件开发时可以参考本地DSH 创造模式里面提供的方法和工具

**base**  
通用助手。默认配置是沙箱脚本和沙箱文件。没有浏览器、MCP、用户自行安装的插件。

**空白 rag**  
继承 base，只改会话启动提示语：知识库还没有资料，不要编造出处。工具与 base 相同。不建向量库，不接收上传。

两条都装进实例。用户不能往市场里加应用。插件写法参考本机 DSH 创造模式里的方法和工具。`/manage/apps` 只读同一份市场数据。

## 8. 渐进执行

一步做完再做下一步。每步结束系统都是可运行的。

### P0 实例能独立启停

launcher + sqlite + 目录创建 + 拉起两个 DSH 子进程。gateway 可以还没有。

完成：两次创建得到两个实例、两个 pid、两个端口、两套目录。停掉一个，另一个仍能响应本机健康检查。

### P1 外面只剩一个入口

加上 gateway。子进程端口不映射出容器。

完成：浏览器经 `http://dsh.xx.yy.com` 进入 gateway。基座在内网时，这条访问通过 frps/frpc 到达，页面仍不经主站转发。基座把本次实例 id 和 cookie 交给主站，主站确认实例、用户、登录状态满足权限后才进实例；不通过或伪造 `X-User-Id` 进不去。容器对外只经过 gateway 这一处。

### P2 脚本进沙箱

DSH 的四类工具改叫 `sandbox-run`。

完成：

- 写入只出现在该实例 `files/`
- `files/` 以外的路径被拒绝
- 环境变量里没有 API Key
- 超时后这次执行结束，DSH 进程还在

不验收 nsjail 的进程级隔离，也不改去用旧稿的沙箱方案。

### P3 base app

先只把 base 放进实例。用户在该实例的 DSH 页面上新建会话并对话。

完成：打开的是该用户自己的 DSH 页面；在页面里让助手写 `hello.txt`，文件出现在该用户 `files/`。

### P4 空白 rag app

把 `rag-blank` 放进同一实例，供页面上新建会话时选择。

完成：在 DSH 页面上能选这个应用新建会话；工具与 base 相同，启动提示语不同；base 会话不受影响。

### P5 一条冒烟路径

一个脚本按顺序做：主站把两个用户分别绑定到两个实例、各自打开自己的实例页面、在页面上分别新建 base 与 rag-blank 会话、做 P2 的隔离检查、停一个实例、重启入口进程后 running 实例回来。

完成：脚本退出码为 0。这是本切片的收口，不另做仪表盘。

### 管理页之前（本切片不执行）

做 `/manage` 之前，先把 `D:\1024\vibe\play-site` 的基础设施抽成 Nuxt 模板 到`D:\1024\vibe\ps-nuxt-tmpl`，再用 `nuxt --template` 创建管理页工程。本切片不抽模板，也不生成页面。

P5 之后，本切片的契约就冻结。0.0.0 的后续切片（数据、提醒、通知、真实 RAG）新增市场条目，不改实例表，不改 `sandbox-run` 的契约。用户与实例的绑定仍只在主站。

## 9. 0.1.0 时怎么接

不在本切片实现，只保证不用推倒：

- 网络与配额：加在现有 `sandbox-run` 上，不另套一层
- nsjail：仍在 `sandbox-run` 里补固定配置，不换成旧稿的 `sandbox-policy`
- 市场：新应用仍是「一份默认配置」，空白 rag 这种只改提示语的条目不必另做工具集
- 工作区：`workspaceId` 从「等于实例」改为真实 id，日志字段不用改名
